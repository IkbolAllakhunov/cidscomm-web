# Cidscomm — контекст проекта для Claude Code

## Что это

**Cidscomm** — адаптивный веб-сайт для платформы взаимодействия детсада
с родителями (расписание, медкарта, чат, фотогалерея). React 19 + Vite,
сейчас работает полностью на mock-данных, без бэкенда.

**Важно про формат продукта:** проект изначально делался как Telegram
Mini App (порт существующего Flutter-приложения), но по решению фаундера
основной канал доставки — **обычный сайт, открываемый по прямой ссылке
в браузере**, а не Telegram. Это осознанный выбор для этапа первых
продаж (см. раздел "Стратегия продаж и канал" ниже) — не путать со
старой версией плана.

Ссылается на техническое задание "Платформа дистанционного взаимодействия
учителей и родителей" (см. краткое содержание ниже).

## Стек

- React 19, React Router 7, Vite 8
- Обычный CSS (без Tailwind), кастомные иконки через классы `ti-*`
- Нет бэкенда — весь стейт живёт в памяти (`src/mock/repository.js`)
- Зависимость `@twa-dev/sdk` (Telegram Web App SDK) в проекте пока
  остаётся, но не является частью основного пути — используется только
  безвредными вызовами `WebApp.ready()/expand()`, которые ничего не
  делают вне Telegram. Можно оставить как задел на будущий
  Telegram-канал (см. ниже), убирать не обязательно.

## Требование адаптивности (активная задача, ещё не сделано)

**Проверено:** сейчас в `src/index.css` нет ни одного media query под
разные размеры экрана (кроме `prefers-reduced-motion`). Вёрстка сделана
только под узкий мобильный экран (наследие Mini App). Это нужно
исправить — сайт должен одинаково хорошо работать:

- на маленьких телефонах (~360-390px ширины)
- на больших телефонах/планшетах
- на ноутбуках/десктопах (широкий экран, мышь и клавиатура вместо тача)

**Важно про источник дизайна:** в Figma-файле фаундера есть макеты
**только для мобильного экрана**, десктопных макетов нет. Это значит:

- Для мобильной вёрстки — источник истины Figma, сверяться с ней
  напрямую (через Figma MCP), переносить точно: отступы, цвета,
  типографику, компоновку.
- Для десктопной/ноутбучной вёрстки — **референса в Figma нет**, её
  нужно спроектировать самостоятельно, а не пытаться растянуть или
  дословно скопировать мобильный макет на широкий экран. При этом
  переиспользовать тот же визуальный язык из Figma (цвета, шрифты,
  скругления, стиль карточек/кнопок), но перестраивать компоновку под
  большой экран по стандартным паттернам адаптивного веб-дизайна:
  - `BottomNav` → боковая навигация (sidebar) или верхнее меню на широком
    экране, не растянутая на всю ширину нижняя панель
  - Контент по центру с ограничением `max-width`, а не на всю ширину
    экрана
  - Многоколоночные раскладки там, где на мобильном был один столбец
    (например, сетка галереи, список групп в админке)
- Если в будущем фаундер добавит десктопные макеты в Figma — они
  становятся источником истины вместо самостоятельно спроектированной
  версии, это нужно будет пересмотреть.

Конкретные задачи для Claude Code:
1. Добавить брейкпоинты (`@media`) как минимум для мобильного,
   планшетного и десктопного диапазонов
2. `BottomNav` (нижняя навигация) — уместна на телефоне, но на широком
   экране обычно ожидается боковая навигация (sidebar) или верхнее меню,
   не растянутая на всю ширину нижняя панель
3. Ограничить максимальную ширину контента на больших экранах (сейчас
   вёрстка рассчитана на полную ширину узкого мобильного экрана — на
   ноутбуке это будет выглядеть растянуто и некрасиво без ограничения
   `max-width` и центрирования)
4. Проверить все ключевые экраны отдельно: логин, профиль ребёнка,
   расписание, чат, галерея, админку — на трёх размерах экрана
5. Фото в галерее — сетка должна адаптивно менять количество колонок
   в зависимости от ширины экрана, не оставаться фиксированной

## Важные особенности и незавершённые места

1. **Реальный поток авторизации сегодня — логин/пароль, не Telegram.**
   `RootSwitcher.jsx` не использует `useTelegramAuth.js` — это
   осознанно оставленный задел на случай, если Telegram понадобится как
   дополнительный канал в будущем, а не незавершённая работа, которую
   надо срочно доделывать.

2. **Неиспользуемые файлы** (нигде не импортируются, задел на будущее):
   - `src/features/auth/PendingApprovalScreen.jsx`
   - `src/features/auth/DevRoleSwitcher.jsx`

3. **Медкарта урезана относительно ТЗ.** Сейчас `child.medicalInfo`
   содержит только `allergies` и `healthGroup`. В ТЗ также требуются:
   хронические заболевания, история прививок, назначенные медикаменты,
   история изменений записи.

4. **Чат только личный (1-на-1).** `repository.js` (`getChat`,
   `sendMessage`) работает по паре `author`/`recipient`. Группового чата
   класса, который требует ТЗ, пока нет.

5. **Данные сбрасываются при перезагрузке страницы** — `db` в
   `repository.js` — это просто копия моков в памяти. Ожидаемо на
   этапе прототипа, не путать с багом.

## Краткое содержание ТЗ (для сверки, что уже сделано / что в приоритете)

**Роли:** учитель, родитель, админ.

**Модули:** расписание+календарь, посещаемость, медкарта (шифрование,
разграничение доступа), чат (групповой класса + личный, архив, TLS, 2FA),
фотогалерея+отчёты+портфолио с тегами детей/событий.

**Нефункциональные требования:** шифрование (TLS + AES), роли+аудит,
2FA/CAPTCHA, GDPR/FERPA/COPPA (право на удаление/доступ/портируемость,
явное согласие на обработку данных детей), микросервисная/модульная
архитектура, 99% uptime, бэкапы, адаптивный UI.

**Приоритеты MVP:** 1) аутентификация+роли, группы, расписание,
посещаемость, медкарта, чат/уведомления, календарь; 2) галерея, портфолио,
подписки, админка. Геолокация и продвинутые функции — вне MVP.

**Дорожная карта после MVP (из исходного ТЗ, ориентир, не обязательство):**
мобильное приложение (push, офлайн-кэш) → биометрия/QR-вход/камера →
геолокация (геозоны, автобусы) → интеграции (LMS, AI-перевод, опросы).
Актуальное решение по нативному приложению — см. раздел ниже, это
пересмотрено относительно исходного ТЗ.

Аналоги, на которые ориентируется продукт: Bloomz, ClassDojo, Procare.

## Стратегия продаж и канал доставки

**Основной канал — сайт, открываемый по прямой ссылке в браузере.**
Не Telegram Mini App. Причины:
- Директор детсада и родители — не обязательно активные пользователи
  концепции "Mini App внутри Telegram", даже если у них установлен
  Telegram. Прямая ссылка в браузере понятна без объяснений.
- Более простой онбординг и более понятный питч на этапе продажи
  директору детсада (человек, принимающий решение о покупке).
- Не создаёт зависимости продукта от политики/ограничений одной
  мессенджер-платформы.

**Что теряем, отказавшись от Telegram как основного канала (осознанно):**
- Бесплатные push-уведомления через Telegram Bot API — на сайте это
  Web Push (на iOS работает только если сайт добавлен на главный экран
  как PWA, с оговорками) либо email/SMS. Для пилота на небольшом числе
  семей это не критично, можно закрывать вручную/email на первое время.
- Бесплатную идентификацию через Telegram `initData` — не критично,
  логин/пароль уже реализован и достаточен для пилота.

**Telegram Mini App не отменяется полностью, а откладывается как
дополнительный канал роста.** Если продукт подтвердит спрос, поверх
ТОГО ЖЕ кода можно добавить Telegram-обёртку (не переписывать заново)
ради бесплатных push-уведомлений в масштабе — сайт и Mini App могут
существовать параллельно на одной кодовой базе.

**Отдельно нужен простой маркетинговый лендинг** (не путать с самим
продуктом) для этапа продажи директору — статическая страница с
описанием, экранами, формой заявки на демо.

## Решение по стеку

- Клиент: React (уже реализован) как адаптивный веб-сайт
- Backend: **Python + FastAPI** (уже заложено в комментариях
  `repository.js`)
- База данных: PostgreSQL
- Файлы/фото: **AWS S3** (см. раздел ниже — выбран вместо Cloudflare R2)
- Чат в реальном времени: WebSockets в FastAPI, без отдельного сервиса
- Уведомления: на старте — email/SMS вручную или простым сервисом;
  Web Push — по мере необходимости; Telegram Bot API — если/когда
  добавится Telegram-канал (см. выше)
- Хостинг фронта: Vercel (уже настроено, см. README)
- Хостинг backend: Railway / Render / простой VPS

**Если в будущем подтвердится спрос на отдельное нативное приложение
(iOS/Android):** рекомендован React Native + Expo (тот же язык, что и
в текущем React-коде; Expo EAS Build снимает необходимость в физическом
Mac для сборки iOS, нужен только аккаунт Apple Developer $99/год и
Google Play $25 разово). Backend на FastAPI при этом не меняется.
Честная оценка — это полноценный второй продукт поверх общего backend,
отдельный этап на месяцы, не "ещё неделя работы". Пока не в приоритете.

**План миграции с моков на реальный backend:**
1. Спроектировать модели в FastAPI 1-в-1 с сущностями из `mock/data.js`
   (users, groups, children, photos, albumsByUser, messages,
   weeklySchedule, scheduleNotes)
2. Реализовать REST-эндпоинты, повторяющие сигнатуры функций из
   `mock/repository.js` (getChildrenByParentId, sendMessage,
   setChildAttendance и т.д.) — чтобы фронтенд менялся минимально
3. Заменить тело функций в `repository.js` на fetch-вызовы к API вместо
   чтения из in-memory `db`
4. Реализовать обычную авторизацию (логин/пароль либо телефон/SMS-код)
   на backend — это основной путь, Telegram `initData` не приоритет
5. Файлы — через AWS S3 (presigned URL, см. архитектуру ниже)

**Что сознательно НЕ делаем сейчас:** отдельные нативные приложения,
Telegram как основной канал, биометрическую авторизацию, геолокационные
функции (геозоны, трекинг автобусов) — всё это отложено до подтверждения
спроса на MVP.

## Решение по хранению фото — AWS S3 (не Cloudflare R2)

Приоритет — юридическая надёжность и зрелость экосистемы безопасности,
а не экономия на egress-трафике. AWS S3 выбран вместо Cloudflare R2 по
следующим причинам:
- Более гранулярный IAM (политики на уровне конкретных объектов, условий,
  ролей) против упрощённых API-токенов у R2
- CloudTrail — подробный лог каждого API-вызова к файлам, лучше для
  расследования инцидентов и юридической защиты
- Поддержка customer-managed KMS-ключей шифрования (у R2 только ключи,
  управляемые Cloudflare)
- Полный выбор конкретного региона хранения данных с многолетней
  практикой (важно, если понадобится соответствие требованиям по
  локализации данных в конкретной юрисдикции)

**Осознанный компромисс:** S3 берёт плату за egress (~$0.09/ГБ после
первых 100 ГБ бесплатно в месяц) — при росте аудитории это станет
основной статьёй расходов на инфраструктуру. Заложить в финансовую
модель по мере роста.

**Важно:** реальная защита детских фото определяется правильной логикой
доступа на стороне backend (короткоживущие presigned URL, проверка
принадлежности ребёнка/группы перед выдачей ссылки на чтение), а не
выбором провайдера самого по себе — на этом должен быть фокус
инженерных усилий, не на бренде облака.

## Архитектура хранения фото (важно — высокая нагрузка ожидается)

Продукт рассчитан на большой поток пользователей, ежедневно загружающих
много фото (учителя — фотоотчёты, родители — просмотр). Наивная схема
"клиент шлёт файл на backend → backend кладёт в S3" здесь НЕ подходит —
backend станет узким местом. Обязательные архитектурные решения:

1. **Загрузка напрямую в хранилище через presigned URL.** Backend никогда
   не принимает и не пересылает байты файла. Поток: клиент запрашивает у
   FastAPI presigned URL → грузит файл напрямую в S3 → сообщает backend
   "готово, вот ключ объекта" → backend сохраняет метаданные и ставит
   задачу на обработку в очередь.

2. **Несколько размеров на каждое фото**, генерируются асинхронно
   воркером после загрузки: thumbnail (~200px, для сетки), средний
   (~800px, для просмотра), оригинал — отдельно, не отдаётся по
   умолчанию. Формат — WebP. Галерея сначала грузит thumbnail, полный
   размер — по клику.

3. **Сжатие на устройстве до отправки** — не грузить необработанные фото
   10+ МБ с камеры/телефона.

4. **Обработка через очередь, не синхронно в HTTP-запросе.** Генерация
   миниатюр не должна блокировать ответ пользователю. Начать можно с
   FastAPI BackgroundTasks, при росте нагрузки — перейти на Celery +
   Redis. Нужна таблица/поле со статусом обработки фото
   (uploading → processing → ready).

5. **Доступ к фото — не публичный бакет.** Это фото детей (персональные
   данные несовершеннолетних, см. GDPR/FERPA/COPPA в разделе ТЗ выше).
   Presigned URL на чтение — короткоживущие, выдаются backend только
   после проверки, что запрашивающий — родитель этого ребёнка или
   учитель этой группы. При удалении — реально удалять объект из
   хранилища, не просто помечать в базе.

6. **Лимиты и валидация.** Лимит размера файла и числа загрузок в день
   на пользователя. Валидация MIME-типа на backend до выдачи presigned
   URL (не доверять расширению от клиента).

## Чек-лист инженерной практики (важно закладывать с самого начала)

1. **Порядок MVP строго по ТЗ.** Сначала: расписание, посещаемость,
   медкарта, чат. Потом: галерея, портфолио, админка. Геолокация — не
   трогать вообще на этом этапе. Не расширять scope "заодно".

2. **Три отдельных окружения (dev/staging/prod)** — отдельные БД,
   отдельные бакеты/префиксы S3.

3. **Единая таблица аудит-лога** с первого дня: `actor_id`, `action`,
   `entity_type`, `entity_id`, `timestamp`. ТЗ требует логирование
   входов, сообщений, изменений данных — не размазывать это по коду
   точечно.

4. **Поле согласия на обработку данных ребёнка в схеме БД с первой
   миграции**: `consent_given_at`, `consent_by_user_id` в таблице
   `children` (GDPR/COPPA-требование из ТЗ). Дёшево сейчас, дорого
   добавлять задним числом на существующих записях.

5. **Автоматические ежедневные бэкапы PostgreSQL** — настроить сразу при
   разворачивании базы, не откладывать. В базе — медданные детей.

6. **Мониторинг ошибок (Sentry, бесплатный тариф)** — подключить сразу
   после первого рабочего backend-релиза, не постфактум.

7. **Как ставить задачи Claude Code:** по одному модулю за сессию
   ("сделай эндпоинты посещаемости"), не "построй весь backend" целиком.
   Каждое новое архитектурное решение — сразу фиксировать в этом файле.
   Код, касающийся авторизации и доступа к медкарте/фото, — ревьюить
   особенно внимательно, не доверять слепо сгенерированной логике
   доступа.

## Как работать в этом репозитории

- Слой `mock/repository.js` — единственное место, которое нужно будет
  заменить на реальные API-вызовы. Не разбрасывать прямые обращения к
  `mock/data.js` по компонентам.
